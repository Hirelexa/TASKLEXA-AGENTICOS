# Phase 7 Report

Status: complete. `BandAdapter` implemented against the interface documented in `docs/architecture.md`, covering both REST commands and inbound WebSocket events, `NOT_CONFIGURED` with zero network calls when no credential is present, full mocked test coverage including the WebSocket dispatch/disconnect lifecycle, and a separate live test gate.

## Deliverables

- `tasklexa_api.integrations.band.client.BandClient`: thin async wrapper over `httpx.AsyncClient` against `https://app.band.ai/api/v1/agent`, Bearer auth, injectable transport for offline testing.
- `tasklexa_api.integrations.band.ws_client`: a `WebSocketConnector` protocol/callable, injectable so `subscribe()` is testable without a real socket. `default_connector()` uses the `websockets` package (already present as a transitive dependency of `uvicorn[standard]` since Phase 1 — no new unverified SDK added).
- `tasklexa_api.integrations.band.adapter.BandAdapter`: every method from the documented interface — `health()`, `create_mission_context()`, `add_participants()`, `send_task_message()`, `send_event()`, `subscribe()`, `sync_backlog()`, `disconnect()`. `subscribe()` opens a WebSocket connection, runs a background task that parses inbound JSON messages into `BandEvent` and dispatches to a caller-supplied handler keyed by `event_type` (sync or async handlers both supported), and returns a `SubscriptionHandle`; `disconnect()` cancels that task and closes the connection.
- `tasklexa_api.schemas.band`: `CollaborationContext`, `Participant`, `ParticipantResult`, `MessageReference`, `EventReference`, `BandEvent`, `SubscriptionHandle`.
- Reused `ProviderNotConfiguredError` / `ProviderCallFailedError` from Phase 4 rather than adding Band-specific exception classes — both were already generic (parametrized by provider name), so no new error types were needed.
- `GET /health/integrations` now calls the real `BandAdapter.health()` for the Band row instead of the Phase 1 `configured_but_unverified()` placeholder, verified live in the running container: still `NOT_CONFIGURED` (correct — no credential), now via the actual adapter code path.
- `apps/api/tests/test_band_adapter_mocked.py`: 15 tests, all offline — `NOT_CONFIGURED` short-circuit (zero HTTP calls, asserted), health LIVE/FAILED mapping including a distinct 401 → "Authentication rejected" case, every REST method's request/response parsing, and — the part that actually needed a fake WebSocket double rather than `httpx.MockTransport` — a full `subscribe()` → event dispatch → `disconnect()` cycle proving a handler only fires for its matching `event_type`, other event types are ignored, and the connection is actually closed.
- `apps/api/tests/test_band_adapter_live.py`: 2 tests, gated on `BAND_AGENT_KEY`/`BAND_API_KEY` being a real environment variable. Both skip in this environment with an explicit reason that also warns the exact REST paths are unverified (see Design Notes).

## Design Notes

**The REST path segments (`/contexts`, `/contexts/{id}/participants`, `/contexts/{id}/messages`, `/contexts/{id}/events`) are an inferred convention, not confirmed against Band's real API.** This is a materially different situation from Phase 4 (OpenRouter) and Phase 6 (Neo4j), where every endpoint/query this project's code calls was directly named in verified documentation. `docs/architecture.md`'s Band section verifies only the two base URLs (`https://app.band.ai/api/v1/agent`, `wss://app.band.ai/api/v1/socket/websocket`), the REST+WebSocket transport split, the mention requirement, and example event type names — and explicitly lists "exact SDK package/version and Python async APIs must be inspected before implementation" as an open question that was never resolved (no live access to Band's actual route-level docs was available in this session). Rather than leave `BandAdapter` unimplemented pending that inspection, or silently guess without saying so, the path names use the most natural REST convention one would expect for "collaboration rooms" ("contexts" as the resource, sub-resources for participants/messages/events) and this is called out explicitly, both in the adapter's own docstring and here, as unverified. See ADR-017.

**WebSocket auth is a guessed query-string token (`?token=<key>&context_id=<id>`).** The verified docs don't specify how the WebSocket handshake authenticates or associates a connection with a collaboration context. A query-string token is a common-enough WS auth pattern to be a reasonable placeholder, but — like the REST paths — this has never been exercised against a real Band WebSocket endpoint and must be confirmed before trusting it.

**`send_task_message`'s mention requirement is not auto-formatted.** `docs/architecture.md` states "Agent messages require mentions of existing participants," but doesn't give the exact mention syntax (e.g., whether it's `@handle`, a structured field, or something else). Rather than guess a syntax and silently inject it into `content`, `target_agent` is passed as its own explicit request field and the caller is responsible for correct message formatting — a wrong guess baked silently into the adapter would be worse than an explicit gap.

**Why the WebSocket dispatch logic gets a hand-rolled fake connection instead of `httpx.MockTransport`.** `httpx.MockTransport` (used for every other adapter's mocked tests in this project) only mocks HTTP requests; `subscribe()`'s core behavior — reading async-iterable messages and dispatching by `event_type` — has nothing to do with HTTP. `test_band_adapter_mocked.py`'s `FakeWebSocketConnection` implements exactly the three methods `BandAdapter` actually calls (`__aiter__`, `send`, `close`), injected via the same `ws_connector` parameter `subscribe()` uses in production — no real socket, no real network, and the test proves the actual dispatch/filtering/cleanup logic, not just that a function ran.

## Known Limitations

- **Nothing here has been exercised against the real Band API or WebSocket endpoint.** This is the least-verified adapter in the project so far (more so than OpenRouter or Neo4j, both of which had concrete documented endpoints). The first real Band credential this project gets should run `test_band_adapter_live.py` — and likely needs actual API/SDK inspection to fix the path names — before this adapter is trusted for anything real.
- No caller uses `BandAdapter` yet — no route, no orchestrator wiring. Phase 7 scope per `docs/architecture.md` was the adapter itself ("Implement BandAdapter after SDK/API inspection. Add REST/WebSocket health behavior."), not integrating it into mission execution. That's a Phase 8+ concern once the Orchestrator exists to actually drive agent collaboration.
- `subscribe()`'s background task has no reconnection logic. `docs/decisions.md` ADR-006 already calls for "subscription, reconnection, and backlog sync behavior" — `sync_backlog()` exists and works, but automatic reconnect-after-drop is not implemented. Adding it without a real WebSocket endpoint to test against would be guessing at failure-mode behavior with no way to verify it; better to add it once Phase 7 gets a live credential.
