# Phase 9 Report

Status: complete. `SimilarwebTool` implemented against the documented interface, registered as the project's first real `ToolDefinition` row so the Phase 5 Capability Resolver can actually discover it, and — per `docs/architecture.md`'s own explicit rule, not just this project's usual caution — it never makes a live network call under any circumstance, because neither the MCP schema nor the REST endpoint schemas are confirmed.

## Deliverables

- `tasklexa_api.integrations.similarweb.tool.SimilarwebTool`: every method from the documented interface — `health()`, `metadata()`, `can_execute()`, `analyze_website()`, `compare_competitors()`, `search_market_signals()`.
- A new `UNVERIFIED` status added to `IntegrationStatus` (`schemas/health.py`) and a new `ProviderUnverifiedError` (`domain/errors.py`) — distinct from `ProviderNotConfiguredError` (no credential) and `ProviderCallFailedError` (a real call was attempted and failed). `UNVERIFIED` means: a credential exists, but there is nothing confirmed to call, so no call is attempted. `docs/integration-status.md` already documented this status value in its "Status Definitions" section since Phase 0 — it was simply never wired into the actual `IntegrationStatus` type until a provider genuinely needed it.
- The project's **first real `ToolDefinition` row**: `apps/api/migrations/versions/40ee52a8c4c8_seed_similarweb_tool_definition.py` seeds `similarweb` (deterministic id, matching `SimilarwebTool.TOOL_ID`) with `status: NOT_CONFIGURED`. Every prior phase's Capability Resolver testing used a fabricated in-memory tool (Phase 5's mocked tests) or none at all — this is the first tool a live `resolve_team()` call can actually find in PostgreSQL.
- Minimal read-only Tool Registry API: `GET /tools`, `GET /tools/{id}` — mirroring the shape of Phase 5's Agent Registry read endpoints, kept read-only since nothing in this codebase creates tools dynamically (they're registered via migration, same pattern as Phase 5's agent seed).
- `GET /health/integrations` now calls the real `SimilarwebTool.health()` for the Similarweb row instead of the Phase 1 placeholder — which, incidentally, had a real bug: it checked `settings.demo_mode` but never checked `settings.similarweb_api_key` at all, so a configured-but-demo-off environment would have silently misreported `NOT_CONFIGURED` forever regardless of credential state. Fixed as part of this upgrade.
- `apps/api/tests/test_similarweb_tool_mocked.py`: 16 tests covering every branch — `NOT_CONFIGURED` (no key, demo off), `UNVERIFIED` (key present, demo off), `MOCK` (demo mode, with or without a key — demo mode takes priority), unsupported-capability rejection in `can_execute()`, and every call method's refusal path plus its labeled demo-data path.
- `tests/integration/test_tool_registry_api.py`: live test confirming the seeded tool is listed and fetchable through the real API with the correct id/capabilities/status, a 404 for an unknown id, and that `/health/integrations` reflects it correctly.
- Fixed a real, unrelated test-contract bug surfaced while adding the `UNVERIFIED` status: `test_health_contract.py`'s label-visibility check hardcoded a scan of `health.py` alone, which broke the moment a status label (`MOCK`, now also `UNVERIFIED`) started living in a provider adapter module instead. Rewrote it to derive the expected labels from `IntegrationStatus` itself and scan `health.py` plus every `integrations/*/*.py` module — a fix that should hold for future adapters too, not just this one.

## Design Notes

**No REST or MCP calls are implemented, full stop — this isn't the same caution level as Phase 7's Band adapter.** For Band, the base URLs were verified but the specific paths weren't, and the choice was implement-with-a-flagged-guess or don't-implement-at-all; Phase 7 chose to guess and flag it loudly. For Similarweb, `docs/architecture.md`'s Rules section is explicit and binary: *"If MCP cannot be verified, keep a provider adapter marked `UNVERIFIED` or implement direct REST only after endpoint schemas are confirmed."* Guessing at REST paths the way Band's adapter does is not one of the two listed options here. So `SimilarwebTool` takes the first option everywhere a real call would otherwise happen: `_require_callable()` always either lets a demo-mode call through or raises — it never reaches for a network call under any credential state. See ADR-020.

**Demo mode takes priority over everything, including a real credential.** If `DEMO_MODE=true`, every method returns labeled demo data regardless of whether `SIMILARWEB_API_KEY` is set — matching `docs/architecture.md`'s "Demo data is allowed only when `DEMO_MODE=true`" rule, which doesn't condition that allowance on credential absence. This means a developer can exercise the demo path deterministically without needing to unset a real key first.

**Demo data embeds its own label inside the payload, not just in the response wrapper.** `ToolResult.demo: bool` marks the whole response, but each `data` dict also carries `"label": "DEMO DATA"` as its own field — so the label survives even if some downstream code only forwards `result.data` and drops the wrapper. `docs/architecture.md`'s rule says demo data "must be labeled `DEMO DATA` in API responses **and UI**" — a UI that only renders `data` fields still sees the label this way.

**Similarweb is finally a real, queryable `ToolDefinition` row — not just a hypothetical.** Phases 5 and 6 both explicitly flagged "no `ToolDefinition` rows exist yet" as a known limitation of the Capability Resolver and graph projection. This phase closes that gap for exactly one tool, seeded the same way Phase 5 seeded agents (a data-only migration with a deterministic id). Because its `status` is `NOT_CONFIGURED`, `repositories.tools.list_tool_definitions(available_only=True)` — the query the Capability Resolver and Mission Orchestrator both already use — correctly excludes it, so nothing about Phase 5/8's existing behavior changes: `digital_market_intelligence`/`website_analysis`/`competitive_intelligence` still resolve only via `market-intelligence-agent`, not via this tool, until a real credential exists and someone updates this row's `status`.

## Known Limitations

- **Nothing here can be exercised against a real Similarweb response**, by design (see Design Notes) — this is not a "not yet" gap the way Band's is, but a deliberate permanent state until a future phase confirms MCP or REST schemas and does the actual implementation work docs/architecture.md's Rules section describes as the alternative path.
- No caller uses `analyze_website`/`compare_competitors`/`search_market_signals` yet — no route, no Agent Runtime (which still doesn't exist anywhere in this codebase; see Phase 8's Known Limitations) to actually invoke a tool during task execution.
- The seeded `ToolDefinition.status` is a static snapshot (`NOT_CONFIGURED`), not computed live from `SIMILARWEB_API_KEY` at query time. If a credential is added later, someone must update this row (or add a new migration) — it won't flip automatically. This mirrors how `AgentDefinition` status already works in this codebase (Phase 5), not a new gap.
