# Phase 6 Report

Status: complete. `GraphService` implemented against the interface documented in `docs/architecture.md`, with idempotent Cypher `MERGE` writes throughout, a projection/repair path that rebuilds a mission's entire Neo4j graph from PostgreSQL on demand, and `/health/integrations` now performing a real authenticated Cypher query for Neo4j instead of a bare TCP handshake.

## Deliverables

- `tasklexa_api.integrations.neo4j.client.Neo4jClient`: thin async wrapper over the official `neo4j` driver's session/run/records API, with an injectable driver for offline testing.
- `tasklexa_api.integrations.neo4j.graph_service.GraphService`: every method from the documented interface — `health()`, `create_mission_graph()`, `add_task()`, `add_agent_assignment()`, `add_evidence()`, `add_decision()`, `add_approval()` (added; see Design Notes), `add_tool_usage()`, `add_outcome()`, `get_mission_graph()`, `find_agents_by_capability()`, `find_related_evidence()`. Every write is `MERGE`-based, so calling any method twice with the same ids converges rather than duplicating.
- `tasklexa_api.integrations.neo4j.dependency.get_graph_service()`: an event-loop-scoped cached instance, extending [[ADR-014]]'s pattern from Phase 5 to the Neo4j driver's own connection pool for the same reason.
- `tasklexa_api.repositories.graph_projection.project_mission()`: fetches a mission's Task/Evidence/Decision/Approval rows from PostgreSQL and replays them through `GraphService` — this one function is both the initial projection and the repair path ("Add graph projection repair path" — repairing a partial/failed projection is just calling it again, because every write is idempotent).
- New minimal read-only repositories needed to gather projection data: `repositories/tasks.py`, `repositories/evidence.py`, `repositories/decisions.py` (also `list_approvals_for_decision`), `repositories/agent_executions.py`. No create/update endpoints were added for these entities — there's still no Task/Decision/Evidence/Approval API in this codebase (see Known Limitations); these repositories exist solely to read what the projection needs.
- API: `POST /missions/{id}/graph/project` (project/repair, returns a `ProjectionReport` with per-mutation results), `GET /missions/{id}/graph` (returns the full `MissionGraph` — nodes and relationships reachable from the Mission node), `GET /agents/by-capability/{capability}` (queries the graph projection, not the PostgreSQL registry — see Design Notes).
- `GET /health/integrations`: Neo4j's row now comes from `GraphService.health()` (`RETURN 1` over an authenticated driver session) instead of the Phase 1 raw TCP check — the same upgrade Phase 4 made for OpenRouter.
- `apps/api/tests/test_graph_service_mocked.py`: 13 tests against a hand-rolled fake Neo4j client (no real driver, no network) — health LIVE/FAILED mapping, correct parameter stringification, empty-list handling, conditional Cypher branches (`add_evidence` with/without task or agent, `add_outcome` with/without a decision), and result parsing for the two query methods.
- `tests/integration/test_neo4j_mission_graph.py`: live end-to-end test against the real Neo4j and PostgreSQL containers — seeds a Mission/Task/Evidence/Decision/Approval directly via SQL (there's no API to create them yet), projects the graph, asserts every expected node label and relationship type is present, **projects again and asserts the node/relationship counts are unchanged** (the actual idempotency proof, not just "it doesn't error twice"), queries `GET /agents/by-capability/research` and confirms the seeded `research-agent` comes back, and cleans up both databases afterward.

## Design Notes

**`find_agents_by_capability` and `find_related_evidence` return graph-native types, not `list[AgentDefinition]`/`list[Evidence]`** (see [[ADR-016]])**.** The documented interface signature says the full domain objects; `GraphService` returns `GraphAgentRef`/`GraphEvidenceRef` instead — minimal projections of exactly what's stored as node properties in Neo4j. Consistent with [[ADR-002]]/[[ADR-003]] ("PostgreSQL remains authoritative... Neo4j is a projection, not the workflow engine"), `GraphService` doesn't reach into PostgreSQL to hydrate full records; a caller that needs the authoritative full `AgentDefinition` or `Evidence` row should fetch it from the existing Postgres repositories by the id this method returns. This keeps `GraphService` a pure, single-purpose Neo4j adapter rather than a second thing that also knows about Postgres sessions.

**`GET /agents/by-capability/{capability}` reflects the graph's current projected state, not the live Agent Registry.** An agent only appears here once it has actually been assigned to a task in some mission *and* that mission has been projected (`POST /missions/{id}/graph/project`). This is a genuinely different data source from `GET /agents` (Phase 5's live PostgreSQL registry, always complete and current) — calling the capability-lookup endpoint before ever projecting anything returns nothing, correctly, because the graph is empty. The live test proves this by projecting a mission with a `research-agent` task assignment *before* checking the capability lookup.

**`add_approval()` was added; it isn't in the documented interface list.** The relationship `(Decision)-[:REQUIRES_APPROVAL]->(Approval)` is in `docs/domain-model.md`'s Graph Projection section, but the Service Interface list in the architecture doc's OpenRouter-style contract section only lists `add_task`/`add_agent_assignment`/`add_evidence`/`add_decision`/`add_tool_usage`/`add_outcome` as the mutation methods — no `add_approval`. Since Phase 2 already has a real `Approval` table with a `decision_id` FK, and the relationship is explicitly named in the projection diagram, omitting it would leave a documented edge permanently unprojectable. Added it following the same shape as the other `add_*` methods.

**`add_outcome()` and `add_tool_usage()` are not reconcilable from PostgreSQL, unlike every other mutation method.** `docs/domain-model.md` never defines persisted fields for "Action" or "Outcome" anywhere outside the Graph Projection relationship list and the high-level `GOAL -> ... -> OUTCOME` flow diagram — Phase 2 never created tables for them. Similarly, there is no "tool usage event" table (`ToolDefinition` exists, but nothing records "agent X used tool Y during task Z"). Both methods exist because the documented `GraphService` interface requires them, and both take a minimal ad-hoc Pydantic input (`OutcomeInput`, `ToolUsageInput`) accepted directly from the caller — but `project_mission()` never calls them, because there's nothing in PostgreSQL to project. This is a real, currently-unresolved gap in the domain model's Phase 2 scope, not a Phase 6 shortcut; see [[ADR-015]].

**`get_mission_graph()` uses a bounded variable-length Cypher path (`[*0..8]`), not APOC.** The Docker Compose `neo4j:5-community` image doesn't ship the APOC plugin, and `docs/architecture.md` explicitly lists "whether local Neo4j Community is sufficient for all MVP graph requirements" as an open question — depending on a plugin that isn't confirmed present would make that worse, not better. Plain Cypher `MATCH p = (m:Mission {id: $id})-[*0..8]-(x)` plus `UNWIND nodes(p)` / `UNWIND relationships(p)` gets the full connected subgraph without any extension, at the cost of being less elegant than an APOC-based traversal.

## Verification Status

- 13 mocked `GraphService` unit tests: all passing, zero network access.
- Live projection + repair test: passing against the actual running containers. Second `POST /missions/{id}/graph/project` call on the same mission produces identical node and relationship counts to the first — the actual idempotency guarantee, verified, not assumed.

- Full combined regression — every mocked test file and every live integration test file (persistence, Mission API, Agent Registry, Neo4j graph) run together in one process: all passing, confirming the event-loop-scoped caching fix (ADR-014) also covers the new Neo4j driver cache.

- `python -m compileall` across all new/changed modules: passed.

## Known Limitations

- **A real bug was found and fixed while writing this phase's `add_outcome` Cypher**: the internal `_mutate()` helper's own `summary` parameter collided with the Cypher parameter `summary` in `add_outcome`'s call (`TypeError: got multiple values for argument 'summary'`), caught immediately by the mocked unit tests before it ever reached a live query. Renamed the helper's parameter to `mutation_summary`.
- No caller triggers graph projection automatically after a Mission/Task/Evidence/Decision write — `POST /missions/{id}/graph/project` must be called explicitly. Wiring this into every relevant write path would couple PostgreSQL writes to Neo4j availability, which [[ADR-002]]/[[ADR-003]] specifically want to avoid; automatic triggering is a natural fit for Phase 8's Orchestrator once it has a clear "on this event, project this" design, not for Phase 6.
- `add_outcome()` and `add_tool_usage()` have no PostgreSQL source and are excluded from `project_mission()` (see Design Notes / ADR-015). Nothing in this codebase currently calls them.
- No Task, Decision, Evidence, or Approval CRUD API exists yet — the live test seeds them via direct SQL. Building those APIs isn't Phase 6 scope (no phase in `docs/architecture.md`'s sequence explicitly owns them); they'll likely arrive alongside Phase 8's Orchestrator or Phase 11's Verifier, whichever actually needs to create them first.
